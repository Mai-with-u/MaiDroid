# 贡献指南

这份文档写给 MaiDroid 提交改动的人：对 MaiBot 的改动要遵守什么原则，怎样保证代码和文档长期可维护，以及怎么发布新版本。构建、测试和代码约定见 [开发指南](development.md)，各包的职责见 [架构总览](architecture.md)。

## 关于 MaiBot 的改动

MaiBot 是上游项目，会持续更新。MaiDroid 装进容器里的是它的仓库代码，用户在设置页点“MaiBot 更新”就会拉到上游的最新提交，所以 MaiDroid 的改动要经得住 MaiBot 的版本变化。

- 非必要不做只对特定版本生效的修改。写死某个版本才有的目录结构、配置项或内部实现，换一个版本就可能失效。确实需要版本要求时，写成“不低于某版本”这样的范围，不要绑定某一个版本。SnowLuma 适配器对 MaiBot 最低版本的要求就是这样处理的（`SnowLumaAdapterScripts.MIN_MAIBOT_VERSION`）。
- 不鼓励也不建议修改 MaiBot 本身，包括它的源码、配置结构和自带插件。这类修改容易在后续更新时产生兼容性问题：在线更新会把受版本管理的文件 `git reset --hard` 到上游，被改过的文件直接还原，不做备份，改动不会保留。
- 功能需要 MaiBot 配合时，按下面的顺序考虑：
  1. 先在 MaiDroid 这一侧解决，比如容器环境、脚本和界面。
  2. 其次用 MaiBot 自己提供的入口，比如环境变量、插件和配置文件。协议确认就是用环境变量预先注入的，插件配置则交给 MaiBot 按默认值生成，MaiDroid 等它生成后再迁移。
  3. MaiBot 本体确实要改的，到 [MaiBot 仓库](https://github.com/Mai-with-u/MaiBot/issues) 提 Issue 或 PR，不要在 MaiDroid 里打补丁。

## 可维护性

MaiDroid 会长期维护，同一段代码也会换不同的人来改。评审时把可维护性放在功能前面：功能正确的改动，只要让后来的人更难找到代码、更容易被误导，或者让文档落后于代码，就不算完成。

### 代码目录结构要直观

- 新人只看目录名和文件名，就该能猜到里面放什么。新建文件前先想一下：别人想找这段逻辑时，会去哪个目录找。
- 包按功能划分，也就是它在产品里是什么（容器运行时、MaiBot、QQ 接入、WebUI），不按技术划分。不要新建 `screen`、`utils`、`common` 这类包，也不要往一个大包里堆不相干的文件。
- 同一件事只有一个显而易见的归属位置。包越来越大时，按功能拆开，不要继续往里加。
- 目录、文件、类的名字要和它现在做的事一致。职责变了就改名、挪位置，不要留着名不副实的名字。
- 增删、移动、改名之后，在同一个 PR 里更新文档里的目录说明，见下面的“文档要保持最新”。

### 名字和说法不能误导人

- 同一个概念在代码、注释、文档、界面文案和提交信息里只用一个名字，同一个名字也只指一件事。引入新术语前先在仓库里搜一遍，看有没有已经在用的说法。
- 名字描述它现在做什么，不描述它的历史或某个具体实现。实现换了，名字跟着换。
- 容易混淆的概念要在文档里点明区别。例如 [消息平台接入](platforms.md) 开头的术语表区分了 SnowLuma 适配器（NapCat 接入方式装的 MaiBot 侧插件）和 SnowLuma 客户端（还没做的另一种 QQ 协议端），以及“接入方式”和“适配器”。
- 同一个名字在不同地方含义不同时，要么改名，要么在定义处写清楚。例如 logcat 标签叫 `TAG`，写进终端输出的行首前缀叫 `LOG_PREFIX`，不混用。
- 注释和文档只写已经确认的事实。拿不准就写明拿不准，从真机排查得来的结论要写清依据，并放在对应的代码旁边。
- 看到过时的注释、已经改名的术语、和代码对不上的说明，当场改掉，不要留给下一个人去分辨哪个才对。

### 文档要保持最新

文档和代码一起改，在同一个 PR 里完成，不留到以后补。改动影响到行为、结构、命名、路径、端口、配置项或约定时，按下表找到要更新的文档：

| 改了什么 | 同步更新 |
| --- | --- |
| 增删、移动、改名包或类 | [架构总览](architecture.md) 的包结构表，README 的“代码在哪” |
| 整体结构、进程、端口、启动或安装流程 | README 的“工作原理”和里面的图，[容器运行时](container-runtime.md) |
| 消息平台接入 | [消息平台接入](platforms.md)，README 里的相关说明 |
| 新增或修改单元测试 | [开发指南](development.md) 的“单元测试覆盖了什么” |
| 构建方式、调试方法、代码约定 | [开发指南](development.md) |
| 用户可见的变化 | `CHANGELOG.md` 的 `## [Unreleased]` |
| 发布流程、贡献要求 | 本文档 |

- 文档里写的路径、类名、命令和端口要能在仓库里找到。重命名之后全文搜一遍旧名字，文档、注释和 README 里的都要改。
- 发现文档和代码对不上，先弄清哪一边是对的，再改错的那一边，当场提交，不要只在评审里提一句。
- 安装包体积、MaiBot 或 MaiDroid 的版本号这类会随发布过期的数字不写进文档。非写不可时，指向能自动保持最新的来源。
- 评审时文档算改动的一部分：代码改了而相关文档没有跟着改的 PR，不算完成。

## 发布与签名

日常开发在 `dev` 分支，`main` 只接收从 `dev` 合入的内容。推送到 `main` 会触发发布流程（`.github/workflows/release.yml`）。日常调试用 `assembleDebug`，调试密钥由每台机器自动生成，不同机器构建出的 APK 签名不同，互相覆盖安装前需要先卸载。

### 发布一个新版本

1. 在 `dev` 上把本次更新的说明写进 `CHANGELOG.md` 最上面的 `## [Unreleased]` 一节。
2. 在 `dev` 上执行 `.\gradlew.bat bumpVersion -Pbump=<major|minor|patch>`，指定 a.b.c 里要 +1 的那一位：
   - `patch` 只加最后一位，例如 0.1.0 -> 0.1.1；
   - `minor` 加中间一位并把最后一位清零，例如 0.1.3 -> 0.2.0；
   - `major` 加第一位并把后两位都清零，例如 0.4.2 -> 1.0.0；
   - `versionCode` 固定 +1。

   任务会同步改写 `app/build.gradle.kts` 和 `CHANGELOG.md`（`Unreleased` 变成带版本号和日期的新一节，并在最上面补一个空的 `Unreleased`）。`Unreleased` 没有内容时任务会报错。
3. 提交，合入 `main` 并推送。
4. 流程读取 `CHANGELOG.md` 最上面带版本号的一节：对应的标签 `v<版本号>` 不存在时，构建、签名并创建 Release，说明就是这一节的正文，标签由流程创建；标签已存在则跳过，所以没有新增版本的推送不会重复发布。

版本号带连字符（例如 `0.2.0-rc1`）会按预发布处理，需要手工写进 `CHANGELOG.md` 和 `versionName`，`bumpVersion` 只处理 a.b.c 纯数字。在 Actions 页面手动运行该工作流只会产出试跑用的 APK，不创建 Release（需要本文件已经在 `main` 上）。
